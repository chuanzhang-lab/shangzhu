# 抽取器 + 运行链路 六维审查与改进方案 — 2026-09-12

> 方法：全部结论均来自**实跑探针**（`extract_params` / `derive` / `quick_scan` 三层直接调用），
> 未采纳推测。核查基线：`main @ b487c0b`（355 passed / 0 failed）。

## 一、总结论

**方案成立，需局部重构** —— 不需要推翻方向（薄引擎 + 置信层 + 单一公式出处是对的），
但**「参数单位契约」存在多头定义**，且抽取器在 4 类常见措辞上漏抽或算错。

- 改动量级：**中等**。核心 2 个文件（`src/router/param_extractor.py`、`src/field_model.py`），
  牵连 1 个（`src/tools/workflow_engine.py` 的 3 处消费点），新增 1 个测试文件。
- 不涉及架构推翻、不新增依赖、不改前端契约。

**最需要你知道的一句**：本轮**不是**「补几个同义词就完了」。
实测暴露出 `gross_margin`（毛利率）这个字段的单位被**三处分别定义成两种**，
主链路靠 `workflow_engine.py:269` 一行 `gm/100 if gm > 1 else gm` 勉强兜住；
一旦有人按 `field_model.derive()` 的公开契约（文档明说「给定输入字段集含缺失 None」）直接调用，
拿到的变动成本率是 **0.994**（应为 0.4）。这是**结构性隐患**，不只是覆盖率问题。

## 二、六维审查表

### 维度 1 · 逻辑性

| # | 具体发现 | 级别 | 影响 |
|---|----------|------|------|
| L1 | `gross_margin` 的单位契约自相矛盾：`field_model.DERIVED_SPECS` 输出 `(1−vcr)×100`=**百分数**，而 `INPUT_SPECS` 声明 `unit:"%"` 却又在公式里 `÷100`；同一字段**输入侧 0~1、输出侧 0~100** | **P1** | `derive()` 是公开 API，按契约传原始输入会算出 0.994 |
| L2 | 主链路正确性依赖 `workflow_engine.py:269` 的 `gm/100 if gm > 1 else gm` —— 用「值大小」猜单位，而 0.4 与 40 都是合法值，**猜不出**。当前恰好正确是巧合（guard 把 60 归一成 0.6，`0.6>1` 为假） | **P1** | 单位推断逻辑本身不成立，是脆弱一致性 |
| L3 | `param_guard.py:381/386` 把 `gross_margin` 与 `variable_cost_ratio` 一并归一到 0~1；`field_model` 按 0~100 处理；`workflow_engine:1272` 用 `>= 50` 比较（0~100 口径）。**三处两种口径** | **P1** | 改任一处都可能静默破坏另两处 |

### 维度 2 · 合理性

| # | 具体发现 | 级别 | 影响 |
|---|----------|------|------|
| R1 | 「公式唯一出处」是已声明的设计契约（`ARCHITECTURE.md` 第 6 节、`field_model.py` 头部注释），但 `workflow_engine.py:250-274` **手写了第二份** `variable_cost_ratio` 四路推导 | **P2** | 契约名存实亡；两份必须人工同步 |

### 9.2 与方案原文的三处偏差（均已给理由）

1. **E5 改走独立正则，而非补进 keyword 列表**
   方案写「补 `食材成本/原料成本` 等同义词」进 `unit_variable_cost.keywords`。
   实测：若直接进列表，通用兜底会把「食材成本占营业额45%」的 45 抽成「每份 45 元」。
   故改用**强制「数字+元/块」的独立正则**（与结构层 ② 既定原则一致）。
2. **验收断言 6 换判据**
   方案写 `grep '从用户毛利率反推'` 应为 0。但该串是**来源标注文案**，被 what-if
   敏感度区间按 `[推算]` 前缀识别 —— 删掉会静默改变区间行为。改用更强的结构断言：
   `gm_ratio` / `float(user_unit_var) / p["price_per_unit"]` / `1 - float(user_gm)`
   在引擎源码中均应为 0（新增 `test_fm11`）。
3. **方案文档一处算术笔误已更正**
   第 117 行原写「`derive({"variable_cost_ratio":0.4})` → `gross_margin = 0.4`」，
   正确是 **0.6**（1 − 0.4）。该错误由 `test_cov_contract_gm_from_vcr` / `test_fm9`
   在实现后立即捕获 —— 正好印证「先写 oracle 再改代码」的价值。
