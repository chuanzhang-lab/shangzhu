# 存储选型决策记录：CN 仓保持 PostgreSQL 唯一主档

> 决定日期：2026-10-07 ｜ 基线提交：`main` @ 存储加固批 1–4 ｜ 决策人：用户（拍板）／执行：存储加固批次
> **一句话决定：本仓（shangzhu / CN）不引入 SQLite。`PostgresStore` 是唯一持久化主档，
> 降级链保持 PG → 本地 JSON 文件 → 内存；PG 侧的成本用工程补齐（装机引导 + 降级可见化 + 可验证备份恢复），
> 而不是靠换后端绕过。**

## 3. 反方论证（诚实摘录：这些话支持 SQLite，本决定不否认它们的合理性）

> 「EN 侧结论已成立：**不换后端**（SQLite 选型正确）、**不加并发复杂度**（实测零错误）。」
> —— `db-sqlite-port-cn-20261006.md`

> 「本地单用户工作台引入一个常驻服务，换来的是它用不到的三种能力（并发写、多用户、JSONB），
> 付出的是一个必须管理的生命周期。」—— 2026-10-07 讨论

> 「PG 不可用表现为『数据存到别处了』，而不是『报错』；把首档放在一个外部服务上，
> 就等于把每一次服务不可用都变成一次静默的数据分流。」

这些论据**成立**。本决定之所以仍然选 PG，是因为它们指向的问题在本仓已被逐条用别的方式消解（第 4 节），
而不是因为它们错了。

## 4. 支持本决定的理由（针对上面每一条）

| 反方论据 | 本仓的处置 |
|---|---|
| 常驻服务生命周期难管理 | 换成**可验证的装机引导**：`scripts/doctor.py` 五层分辨（驱动/服务/库/权限/表），每层给可粘贴命令；`STORE_BACKEND=pg` 档位可在启动前体检并拒绝降级 |
| 「不可用 → 静默分流」是最危险的失败形态 | 换成**降级可见化**：`/health` 8 个诊断字段 + 页面顶部降级横幅（文件/内存两种红色等级）+ 恢复时孤儿数据告警 + `persist_warning` 当场提示本轮未落盘 |
| PG 的运维成本（备份/恢复） | 换成**可验证恢复**：`-Fc` + 写完即校验 + `restore_db.sh` 四档 + `make drill` 演练（2026-10-07 实测：648 任务/1471 消息与生产库一致） |
| SQLite「零配置」 | 承认差距：第一次上手确实要多一步装 PG。补偿是 doctor 把这一步变成「一条命令 + 一步一验」，而不是盲测 |
| SQLite 的迁移成本已由 EN 付过 | 这不是 CN 选 SQLite 的理由，反而是**不选**的理由：EN 走的是「先写 → 接管 → 25m48s 实测发现问题 → S1–S7 回头加固」，CN 若跟进等于再付一轮维护与加固 |

**另一个决定性事实**：SQLite 方案要求删除 `LocalFileStore`，把降级链从三档压到两档，
并把「降级可见性」全部押在 `/health` 观测位上——而那套观测位在原方案写作时**尚不存在**。
方案自己也把这条列为遗留风险（「C5 未落地而先切换，将出现『降级了但前端不知道』的窗口期」）。
本决定选择的顺序相反：**先把可见性与可恢复性补齐（已完成），再谈要不要换**。

## 5. 边界声明：双副本存储层「有意分叉」

- EN 仓：`SqliteStore`（面向其受众与分发渠道）；CN 仓：`PostgresStore`（本仓）。
- 两仓仍是同构双副本，**但存储层是显式豁免层**：`scripts/copy_drift_report.py` 的 11 条
  「事故形态不变量」不覆盖存储实现，因此不会红——这是设计如此，不是漏检。
  任何「拿 EN 的 SqliteStore 来对齐 CN」的动作，必须先回来改本决策记录。
- 两仓共有的**行为契约**（`BaseStore` 九方法 + `add_turn` 原子回合）仍应保持语义一致；
  若 EN 侧新增 `health_check()` / `purge_deleted(days)` 一类接口，CN 可按需跟进，不必同批。

## 6. 重开条件（什么情况下应该重新评估本决定）

出现下列任一硬需求时，重开评估（从第 3 节的反方论证开始，而不是从零）：

1. 需要面向**非开发者渠道**分发（手机 App / APK / 免安装包），用户无法 `git clone` 与装 PG；
2. 出现「零外部服务依赖」的硬约束（合规、离线交付、客户环境不允许常驻服务）；
3. PG 侧的可见化/恢复机制在真实使用中反复失效（届时先修机制，再考虑换后端）。

## 7. 本决定带来的、明确接受的代价

- 首次上手多一步「装并启动 PostgreSQL」——已由 doctor + README 装机排障表缓解，不会消失；
- 本机需长期运行一个 PG 服务（`brew services`/systemd），存在「装了没起」的常态风险——
  由降级链 + 横幅提示兜住（数据落文件、重启不丢、可迁回）；
- 与 EN 仓存储层永久分叉，双份维护成本（已用第 5 节的边界声明圈定范围）。
