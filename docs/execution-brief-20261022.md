## 3. 关键背景（计划里写不下、但不知道就会做错的部分）

### 3.1 事故溯源（每一处的"为什么这么做"）
- **为什么 PUT 必须成为唯一写入口**：现在参数只能经 NL 抽取进引擎，2026-10-03 线上「客人 80 人」被记成「员工 80 人」，用户完全不可感知。表单让错误可被人眼拦截。
- **为什么确认层默认开**：同上——用户「从来没输入过员工80」却看到系统显示员工80，这种"系统替你编了个数"的体验必须封死。可跳过是设置项，不是默认值。
- **为什么 LLM 规整层推迟**：确认层若见效，那一层可能永远不需要做。Sequencing 上它排在最后。
- **为什么不动 field_model**：那里已经是形式化的推导图（INPUT_SPECS/DERIVED_SPECS/derive()），是本次表单 schema 的数据源，改它等于动引擎。

### 3.2 歧义史（避免执行时走回头路）
- 「员工80」**不是**用户输入的——用户输入的是客人语境（`客人80人`），被 `_HEADCOUNT_RE` 抽成 employee_count。用户从没输入过"员工80人"。
- 线上 hostname 叫 `shangzhu-en.app.workbuddy.host`，但部署的是**中文仓**代码（"en" 只是 workbuddy 槽位名）。不要因为 URL 里有 en 就去改 EN 仓。
- 演示实例 `STORE_BACKEND=memory` 是 README 声明过的**刻意设计**（内存档演示，数据重启即丢），不是故障。本次要修的是 worker 数导致的打散，不是把它改成持久化。

### 3.3 已实证的事实（有探针脚本，别重 suspect 别重复验证）
- 代码层 merge/hydrate/persist **没有**跨轮丢失 bug（单进程 + file store 五轮完整累积）。
- 线上丢失 = memory store + 多 worker 轮询（复刻实验中第 4 轮 params 全空）。
- 误抽确知：`客人80人`→employee_count=80；`50人/天`→daily_traffic=50 且 employee_count=50 双写；误抽值会覆盖真值（80 被 50 覆盖）。
