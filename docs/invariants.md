# 不变量账本 / Invariants Ledger

「点名抓」的实体：每条被钉住的断言一行。规则（技能 §9）：

1. 每个线上事故 / 每个被断言抓出的缺陷 → 至少一条新条目 + 至少一条新断言；
2. 条目的「类名」是缺陷的抽象（不是个案复述），供后续改动做类匹配；
3. **没有对应断言的条目不许存在**——"知道了"不记账，钉住了才记。

## INV-001 [L1] 人工未提供时，不得给出「确定」的利润/保本结论

- **不变量**：员工数或薪资缺失时，引擎可以继续按「人工 = 0」近似算数值，但**必须在
  三处点名人工缺失**：月利润徽章、保本判定、固定成本来源标注；不得给出
  `🟢 盈利` / `🟢 可达保本` 这类确定判定。
- **断言**：`tests/test_engine_missing_labor_disclosure.py`（7 条，两面用例）
  - 缺陷侧 4 条：利润徽章 / 保本徽章 / 固定成本来源标注 / 渲染层「月利润」行
  - 防误伤侧 3 条：人工齐全时 `🟢 盈利`、利润 21000、保本 37 分毫不动
- **来源**：2026-10-28 抽取层修复 `4381dec` 后暴露。抽取层不再把「客人80人」误落
  `employee_count`，于是人工缺失的会话显著变多；实测缺人工时引擎仍输出
  `monthly_profit=31000` 并标 `🟢 盈利`、`daily_breakeven=16`（不含人工，门槛被低估），
  与 README 的核心主张「绝不把未知当 0 硬算出一个确定的答案」正面冲突。
- **类名**：
  1. **软缺口的「并标注」半边未兑现**——`_check_sufficiency` docstring 明文约定
     「按 0 计**并标注**」，只兑现了前半（按 0 计），标注只落在 basis/gaps，
     数值与徽章上是干净的；
  2. **同一结论在两处各算一次**——`workflow_engine:1328` 与 `formatter:164`
     各自按利润正负算徽章，引擎侧的降级被显示层无声丢弃。
- **修复**：`workflow_engine` 引入 `_labor_uncounted`（`monthly_labor is None`）→
  利润/保本徽章降级为 `🟡 待定（人工未提供…）`，固定成本来源标注追加
  「（人工未提供，未计入）」；`formatter` 利润徽章改为以引擎 `status.profit`
  为唯一出处，不再另算。
- **验证**：红位精确吻合（撤两处实现 → 4 红；还原 → 7 绿）；全量 613 passed。
