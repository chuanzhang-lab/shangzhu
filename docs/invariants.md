# 不变量账本 / Invariants Ledger

「点名抓」的实体：每条被钉住的断言一行。规则（技能 §9）：

1. 每个线上事故 / 每个被断言抓出的缺陷 → 至少一条新条目 + 至少一条新断言；
2. 条目的「类名」是缺陷的抽象（不是个案复述），供后续改动做类匹配；
3. **没有对应断言的条目不许存在**——"知道了"不记账，钉住了才记。

## INV-001 [L1] 必有固定成本项（租金 / 人工）未提供时，不得给出「确定」的利润/保本结论

- **不变量**：**租金或人工**任一缺失时，引擎可以继续按「缺失项 = 0」近似算数值，
  但**必须在三处点名缺了什么**：月利润徽章、保本判定、固定成本来源标注；不得给出
  `🟢 盈利` / `🟢 可达保本` 这类确定判定。此外缺失项必须进「还差这些参数」缺口清单。
  - 只点名**必有主体**（租金 / 人工）。细项（水电/包装/提成/其他固定）缺失是常态，
    不点名以免噪音；**用户显式给 0 属已知值，不算缺失**，不得标注。
- **断言**：`tests/test_engine_missing_labor_disclosure.py`（7 条，两面用例）
  - 缺陷侧 4 条：利润徽章 / 保本徽章 / 固定成本来源标注 / 渲染层「月利润」行
  - 防误伤侧 3 条：人工齐全时 `🟢 盈利`、利润 21000、保本 37 分毫不动
- **来源**：2026-10-28 抽取层修复 `4381dec` 后暴露。抽取层不再把「客人80人」误落
  `employee_count`，于是人工缺失的会话显著变多；实测缺人工时引擎仍输出
  `monthly_profit=31000` 并标 `🟢 盈利`、`daily_breakeven=16`（不含人工，门槛被低估），
  与 README 的核心主张「绝不把未知当 0 硬算出一个确定的答案」正面冲突。
- **类名**：
  1. **软缺口的「并标注」半边未兑现**——`_check_sufficiency` docstring 明文约定
     「按 0 计**并标注**」，只兑现了前半（按 0 计），标注只落在 basis/gaps，
     数值与徽章上是干净的；
  2. **同一结论在两处各算一次**——`workflow_engine:1328` 与 `formatter:164`
     各自按利润正负算徽章，引擎侧的降级被显示层无声丢弃。
- **修复**：`workflow_engine` 引入 `_labor_uncounted`（`monthly_labor is None`）→
  利润/保本徽章降级为 `🟡 待定（人工未提供…）`，固定成本来源标注追加
  「（人工未提供，未计入）」；`formatter` 利润徽章改为以引擎 `status.profit`
  为唯一出处，不再另算。
- **验证**：红位精确吻合（撤两处实现 → 4 红；还原 → 7 绿）；全量 613 passed。

### INV-001 第二轮（2026-10-30）：租金是同构实例，首轮漏修

首轮只修了人工。按类名回扫软缺口清单发现**租金完全没修**：缺租金时
`profit=29000` → `🟢 盈利`、`fixed=10000` src「组件求和(人工[用户])」零提示、
`breakeven=21` → `🟢 可达保本`，且 `_check_sufficiency` 的 gaps 里**根本没有月租金**
（它只在 `key_fields` 参与 coverage 统计），连"还差什么"都不显示——比人工那个更隐蔽。

- 修复：`_labor_note` → `_req_note`（未计入的必有项清单：租金 + 人工）；徽章降级判据
  从 `monthly_labor is None` 改为按 `param_sources` 判缺失；gaps 补「月租金」项。
- 验证：新增 4 条租金断言 + 2 条 None 吞值断言；撤实现 → 6 红精确吻合 → 还原 → 14 绿；
  全量 **620 passed** + 5 个 e2e 全 PASS。

## INV-002 [L1] 缺失不得被数值化——`x or 0` 会把未知伪装成「推算」值

- **不变量**：参数缺失时，引擎内部必须保持 `None` + `[缺失]` 来源标注，**不得**用
  `or 0` 把缺失转成 `0`（更不得标成 `[推算]`）。`[推算]` 看起来是有依据的数值，
  比 `[缺失]` 更危险：用户会把它当成算出来的结论。
- **断言**：`tests/test_engine_missing_labor_disclosure.py`
  - `test_none_valued_employee_count_not_swallowed_to_zero`：
    `employee_count=None` → `monthly_labor` 必须 `None` 且 src 以 `[缺失]` 开头
  - `test_none_valued_employee_count_profit_not_confident`：承上，徽章不得仍是 `🟢 盈利`
- **来源**：2026-10-28 排查 INV-001 时顺带发现并标为"可达性未追平"；2026-10-30 实测
  **确认可达**——传 `employee_count: None` 时 `labor_present` 用「键存在」判定
  （`k in raw_params`）为真，随后 `float(p.get("employee_count") or 0)` 把 None 吞成 0，
  产出 `monthly_labor=0.0` + src `[推算] 裸薪0×(1+0%负担)`，而引擎自己的
  `basis.employee_count` 明明写着 `missing`。
- **类名**：**判据用「键存在」而非「值非空」** + **`or 0` 把未知数值化**（Round 3 已点名
  过同一族：`x or None` 吞零 / 吞缺失）。修复点是判据，不是把 `or 0` 改成别的兜底值。
- **修复**：`labor_present` 改为 `raw_params.get(k) is not None`（`staff_count` 分支同理）。
- **教训**：上一轮我据推测写下"可达性未追平"就收工，等于把一个可达缺陷挂成待定。
  **凡"未追平"的可达性判断，必须当场补一条探测用例定性**，不能留给下一轮。

### INV-001 范围边界（2026-10-31 用户拍板，不再重开）

只点名**租金 + 人工**两项必有主体。细项（水电/包装/提成/其他固定）缺失**不标注**，
理由：金额小、常态缺失，标注会让 `🟡 待定` 泛滥成噪音，反而稀释主体项的警示。
若日后要扩到细项，需独立提案，不得作为 INV-001 的"补齐"顺手做。

## INV-003 [L1] 不得跨字段反填——`employee_count` 不许补 `founder_count`；守护测试不得固化已废弃的错误契约

- **不变量**：创始人 ≠ 员工。`founder_count` 只能来自抽取层的真实口径
  （`param_extractor._extract_founder_count`），**任何层都不得**用 `employee_count`
  的值补位，也不得在缺信息时臆造默认值。缺失即字段缺席（宁缺勿填）。
- **断言**：`tests/test_cleanup.py::test_cleanup_project_manager_single_parser`
  - 正常侧：『创始人3人』→ `founder_count == 3.0`
  - 防误伤侧：『员工3人』→ 结果里**不得出现** `founder_count` 键
  - 缺失侧：无团队信息 → 字段缺席，不得补默认 `1`
  （另有 `tests/test_phase3_session_alignment.py::test_founder_count_not_employee_count`
  在抽取层同侧把关，两者现语义一致）
- **来源**：2026-10-31 清理 B 路径死代码时发现。`src/tools/project_manager.py`
  曾写 `params["founder_count"] = int(raw["employee_count"])`，与 2026-10-24
  抽取层 `4381dec` 引入的「创始人 ≠ 员工」分流语义正面冲突。
- **类名**：
  1. **跨字段反填**——抽取层把 A/B 拆开后，下游残留的合并映射不会报错，
     只会把语义静默搞反；抽取层修得越正确，这处残留越显得荒谬。
  2. **同一契约被两处互相矛盾的断言同时"守护"**——本仓库同时存在
     `test_cleanup.py:47`（断言员工数必须映射到 founder_count）与
     `test_phase3_session_alignment.py:300`（断言两者必须分流）两条断言，
     因分处不同文件、不同被测对象而**长期并存且各自飘绿**，缺陷被测试掩护而存活。
     **修 A 层的语义，必须回扫所有断言该语义的测试，不能只看改动文件的邻居。**
- **补充事实**：该处并非纯粹死代码——`project_manager` 无任何调用方，但
  `test_cleanup.py` 正在**固化它的错误行为**；且实测用户明说『创始人3人』时
  旧代码仍返回 `founder_count=1`（默认值），因为它压根没读抽取器的真实口径。
- **修复**：删除反填分支，`founder_count` 并入透传字段列表直取抽取器；同步修正
  `test_cleanup.py` 的错误断言并补两面用例。
- **验证**：撤实现 → 红（实测三条新断言各自独立咬住：得 1 / 得 3 / 得 1）；
  还原 → 绿。全量门禁见下。
